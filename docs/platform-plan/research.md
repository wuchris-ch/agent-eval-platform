# Research synthesis and decisions

Research checked **September 11, 2026**. Primary engineering articles, project documentation and original papers inform the proposal. Documentation describes supported behavior; it does not prove this checkout's implementation or deployment. No external framework was installed or benchmarked in this task. Version pins must be selected and tested in the implementation spikes, not inferred from a moving documentation page. The July document's version table is historical, not a current compatibility matrix.

## Findings that affect this design

| Source and date | Evidence and implication |
|---|---|
| Anthropic, [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), January 9, 2026 | Distinguishes tasks, trials, graders, trajectories and outcomes; recommends inspecting transcripts, calibrated graders and separate capability/regression suites. Adopt these distinctions and grade achieved state where possible. Our proposed controls and milestone thresholds are local design decisions. |
| Anthropic, [Quantifying infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise), February 5, 2026 | Reports a six-percentage-point spread across resource configurations in its Terminal-Bench experiment. This is an author-run result, not an expected gain here. Record resource requests, hard limits, enforcement mode and concurrency. Calibrate locally; do not copy its resource multiplier or label every OOM an agent defect. |
| LangChain, [How We Built LangSmith Engine](https://www.langchain.com/blog/how-we-built-langsmith-engine-our-agent-for-improving-agents), May 19, 2026 | Describes screening compact trajectories, deeper investigation, evidence-linked issues, and proposed evaluators/cases. Reuse the workflow pattern with human review and independent acceptance. Defer autonomous diagnosis until basic annotation and dataset provenance work. |
| LangChain, [New in LangSmith Engine](https://www.langchain.com/blog/new-in-langsmith-engine-2x-better-issue-detection), August 25, 2026 | Its reported greater-than-twofold detection improvement is on internal benchmarks. It is not comparative proof for this platform. The article presents automated verification as future work at publication; issue discovery and a proposed fix should not be confused with independently verified improvement. |
| Yao et al., [tau-bench](https://arxiv.org/abs/2406.12045), 2024 paper, checked September 11, 2026 | Evaluates interaction with policy-governed tools and database outcomes, and introduces repeated-success reliability. Use task-level state checks and report all-trials success separately from at-least-one success. Its simulated users are another variable to version and audit. |
| Sierra Research, [tau2-bench repository](https://github.com/sierra-research/tau2-bench), current docs checked September 11, 2026 | Dual-control environments illustrate why user actions and environment state matter beyond the assistant's final sentence. Consider a small imported task pack later, with its simulator and dependencies pinned. Do not make it the mandatory personal workflow. |
| Gupta, [ReliabilityBench v1](https://arxiv.org/abs/2601.06112v1), January 3, 2026 | Preprint proposes consistency, input perturbations and controlled tool failures as separate axes. Useful experimental design inspiration; its reported model comparisons are not independently reproduced here. Keep fault severity and input variants explicit instead of one composite reliability number. |

The differentiator should be reliable evidence and useful experiments on Chris's actual agents. A new trace viewer or an agent that generates its own goldens would add little confidence. A failed-case investigation that ends in a reviewed case, a calibrated grader, a paired experiment and a reproducible gate decision is a stronger engineering outcome.

No adapter compatibility, throughput, cost saving or hosted readiness is claimed from these sources. For any dependency adopted, the spike records exact version, license, fixture result, failure behavior and maintenance cost. Avoid keeping two schedulers authoritative over the same attempt.

## Infrastructure decisions

**One service first, bounded jobs later.** Use Python for domain and orchestration, with a thin HTTP layer and a UI over the same services as the CLI. SQLite fits one local writer. PostgreSQL becomes necessary for shared claims, budget reservations and team access. Its documented `SKIP LOCKED` is suited to queue-like access but gives an inconsistent view, so use it only for transactional work claiming, not reporting. [PostgreSQL 18 SELECT documentation](https://www.postgresql.org/docs/18/sql-select.html), checked September 11, 2026.

**Kubernetes runs processes; the platform owns experiment truth.** A Job can start the same program more than once even with one completion and no parallelism. Use immutable attempt IDs, lease fencing, idempotent finalization and reconciliation. Set `backoffLimit: 0` for platform-managed attempts, explicit deadlines, and cleanup only after evidence persistence. Those are proposed choices to test. [Kubernetes Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/), checked September 11, 2026.

**Do not introduce Redis, Kafka, ClickHouse or a service mesh initially.** The first workload is a few deliberate experiments on one laptop, not a demonstrated event-volume problem. An SQL queue and transactional outbox are enough for the proposed multi-worker stage. Revisit after measured queue latency, database contention or telemetry volume exceeds a documented target.

**Do not market ordinary k3s isolation as a hostile-code security boundary.** Preserve the current protected evaluator topology. Hosted untrusted execution needs a tested sandbox runtime or disposable VM, separated evaluator credentials, restricted egress and independent control-plane authority. This is a threat-model requirement, not a claim that adding a RuntimeClass completes security.

## Decisions to revisit with evidence

1. If Phoenix's installed experiment UI satisfies comparison and annotation needs without semantic loss, reduce the custom UI to launch/provenance/gates rather than duplicating those screens.
2. If the Inspect spike preserves protected grading, attempts and all legacy outcomes with less maintained code, use it behind an execution adapter. Migration still needs contract tests and an exit path.
3. If jobs span days with human waits and several external effects, compare Temporal against measured maintenance of the SQL reconciler.
4. If only one user and one worker remain, do not force PostgreSQL or hosted deployment merely to advance a diagram.

Current recommendation: preserve this repository's evaluators, implement the missing experiment lifecycle, prove daily value with two distinct agents, then scale only after recovery and measurement semantics are demonstrated.
